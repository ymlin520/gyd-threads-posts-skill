# 語氣、開頭與六種結構

## 人設與讀者

- 用第一人稱「我」寫。身分是長年幫客戶架站、代管、救援 WordPress 網站的實務工作者（GOT YOU DESIGN／hostswp.com）
- 讀者是台灣中小企業老闆、行銷小編、接案設計師，以及想自己架站的人
- 語氣像懂技術的朋友在提醒：不說教、不賣弄。術語第一次出現時用白話帶過，例如「業界叫 NAP」

## 用字與格式

- 台灣繁體中文：外掛、主機、快取、網域、後台、預設、資料庫、網站。不用插件、服務器、緩存、域名、默認、數據庫
- 一段 1 到 3 句，段落之間空一行
- 條列用「・」，編號清單用 1️⃣ 2️⃣ 3️⃣，對照用 ❌ ✅。除此之外不加 emoji
- 正文長度 220 到 380 字，不含主題標籤
- 倒數第二段放一句讓人記得住的收束句，例如「AI 引用的是答案，不是口號。」
- 最後一句是讀者馬上答得出來的具體問句，問他自己網站的現況。例如「你的網站後台，現在有開兩步驟驗證嗎？」不要用「你覺得呢？」這類空泛問句
- 問句的下一行，加一句跟這篇主題相關的詢問邀請，讓卡住的讀者留言或私訊問 WordPress 問題。例如「不確定哪些外掛刪了會出事，可以私訊把外掛清單傳給我，我幫你看」「不知道主機後台去哪設 Cron，留言說你用哪一家主機」。每篇依主題各寫一句，不要整批用同一句「有問題歡迎私訊」。這一句是使用者要的導客入口，也能帶動留言數
- `firstComment` 放詢問管道與 hostswp.com（網址放留言，不放正文）。可以依類別準備幾種說法：資安維護、WooCommerce、SEO、其他
- 最後一行放 2 個主題標籤，例如 `#WordPress安全 #網站維護`。第一個放最精準的主題
- 正文不放網址。要導流時，把網址寫在 posts.js 的 `firstComment` 欄位

## 第一句

- **最好用**，反轉或提醒句（這個帳號 1.23 倍）：
  - 「X，不代表 Y。」
  - 「X，通常不是因為 Y。」
  - 「卡住的不是 A，是 B。」
- **可以用**：
  - 短句破題
  - 一句具體場景：「改版上線那天大家都很開心，兩週後，搜尋流量掉了一半。」
  - 放進引號的常見說法：「官網最近三個月都沒人詢問」
- **不要用**：
  - 問句當第一句（0.65 倍）
  - 「大家好」「今天來聊聊」這類開場
  - 課本式定義：「SEO 是指⋯⋯」

## 每篇都要是 WordPress 的事

這是 WordPress 專業帳號，讀者追蹤是為了學 WordPress。一篇好的貼文，至少要讓讀者知道在 WordPress 裡具體要去哪裡、做什麼：
- 後台路徑，例如「設定」→「閱讀」、「工具」→「網站健康狀態」
- 外掛或主題名稱與對應設定，例如 Rank Math 的「連結」、Elementor 的「歷史紀錄」
- WooCommerce 設定，例如「設定」→「商品」→「庫存」
- 檔案或常數，例如 wp-config.php、WP_POST_REVISIONS

自我測試：把文中跟 WordPress 有關的字眼拿掉。整篇還能原封不動發在任何網站行銷帳號，就代表太泛，要改寫或換題。

主題可以寫行銷、UX、法規或數據，但切入點必須落在 WordPress 上。例如不寫「隱私權政策要寫什麼」，改寫「WordPress 內建的『設定→隱私』和『匯出／清除個人資料』怎麼用」。

後台選項名稱沒有把握時，寫功能描述，或加上英文原名（例如 Individual use only），不要自己編一個看起來像真的中文選項名稱。

## 六種結構（同一批輪流用）

整批都套同一個模子，連著讀會很膩，使用者已經明確反映過。相鄰兩篇不要用同一種結構。

### 1. 故事型

骨架：場景 → 事情怎麼走歪 → 真正原因 → 怎麼做 → 收束句 → 問句
圖卡：`num` 或 `numsub`

寫成「很常見的情境」，不要捏造特定客戶、真實姓名或成效數字。可以寫「這種狀況比想像中常見」，不要寫「上個月某客戶改完詢問多了 40%」。

範例開頭：「三年前買的萬用主題，現在變成網站最大的包袱。」

### 2. 迷思對照型

骨架：開頭 → 3 到 4 組「❌ 誤會 ／ ✅ 事實」→ 比較安全的做法 → 收束句 → 問句
圖卡：`vs`

範例開頭：「網站上的圖片，『網路上找得到』不代表可以用。」

### 3. 自我檢查型

骨架：開頭 → 「花 3 分鐘檢查這 N 件事」→ 編號題目（每題都是一個看得到、做得到的動作）→ 怎麼改 → 問句（例如「有幾題不及格？」）
圖卡：`num`（4 到 5 項）

範例開頭：「結帳頁掉單，通常不是因為價格。」

### 4. 算帳型

骨架：開頭 → 一個讀者自己算得出來的情境數字 → 這段時間會發生什麼 → 怎麼避免 → 收束句 → 問句
圖卡：`stat`

數字必須是情境推算，例如「週五 20:00 掛掉，週一 09:00 才發現，中間 61 小時」。不要引用來源不明的統計數字。

### 5. 立場型

骨架：「我通常會勸退／我不建議」→ 理由 → 替代做法（可以用「不要寫 A，改寫 B」）→ 收束句 → 問句
圖卡：`dot` 或 `vs`

範例開頭：「新網站一開始就想搶『網站設計』這種大關鍵字，我通常會勸退。」

### 6. 經典條列型

骨架：反轉開頭 → 常見原因條列 → 處理順序 → 收束句 → 問句
圖卡：`dot` 或 `numsub`

範例開頭：「Cloudflare 一開，網站反而出狀況，通常不是 Cloudflare 的問題。」

## 準確性底線

讀者會照著文章去改自己的網站，寫錯會直接傷到信任。

- 工具、外掛、設定名稱必須真實存在，而且現在還能用。例如 LINE Notify 已在 2025 年停止服務，不要再推薦。版本號或價格不確定就不寫
- 不捏造百分比、研究報告、客戶名稱或成效數字
- 示範用的價格或時程，要在文案裡標註「示範寫法」
- 法律、稅務、個資類題目只講原則，並加一句「實際狀況建議諮詢律師（或會計師）」
- 資安題目只寫防護和檢查方法，不寫攻擊步驟

## 完整範例（迷思對照型，已實際產出）

```
網站上的圖片，「網路上找得到」不代表可以用。

越來越多網站主收到信，說網站上某張圖侵權、要求賠償。最常見的誤會有這幾個：

❌ 註明出處就可以用
✅ 註明出處，不等於取得授權

❌ 圖是前一個廠商放的，跟我無關
✅ 網站是你的，責任通常也落在你身上

❌ 已經刪掉就沒事了
✅ 對方存證之後，刪掉不代表不用處理

❌ Google 圖片搜得到，就是公開的
✅ 公開能看，不等於可以商用

比較安全的做法：
用 Unsplash、Pexels 這類明確可商用的圖庫；付費圖庫保留授權紀錄；網站外包時，合約寫清楚素材授權由誰負責。

真的收到求償信，怎麼回應建議先諮詢律師，不要急著付款或置之不理。

你網站上的每一張圖，你知道是從哪裡來的嗎？

#網站經營 #圖片授權
```
